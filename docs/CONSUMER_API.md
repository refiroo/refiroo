# Consumer API (Product 0.9)

Status: accepted scope for 0.9, alongside the integration items already listed in ROADMAP.md.
All decisions (C-D1 to C-D16) are accepted as of 2026-09-29 and listed at the end.

## Security (0.12)

Security is not part of 0.9. Once the 0.9 APIs work, the 0.12 security release adds authentication and
authorization to the backend, the frontend and the consumer APIs together (ROADMAP 0.12). The target
design, recorded now so 0.9 does not close it off:

- **No API-key credentials.** No credential ever appears in a URL, and the engine issues no static
  keys for callers. (The `apiKey` in routes is a definition name, not a credential.)
- **OAuth 2.0 with JWT.** The engine provides OAuth 2.0 and issues JWT access tokens. Systems calling a
  consumer API authenticate as OAuth clients and are authorized per consumer API definition.
- **Webhooks are signed with an HMAC key** per subscription, generated by the engine, shown once and
  rotatable.
- **Administration in the UI** for both: OAuth clients and their access, and webhook subscriptions and
  their signing keys.

Until 0.12 the consumer API is unauthenticated, like the management API, and a deployment exposes it
only where that is acceptable. The `{apiKey}` segment in the routes below is not a credential; see
[The `apiKey`](#the-apikey).

## Why a second API tier

The API in API.md is the **management API**. It maintains models and data: change sets, publication
history, typed filters, optimistic concurrency and graph-shaped responses. The UI and the tools that
synchronize or administer reference data use it.

The **consumer API** is for the systems that *use* reference data in integration flows. Those systems
look a value up, translate it between systems and read lists of it. They need:

- one object shape for every object type, so a flow does not need a parser per type;
- a single lookup that finds an object by any of its identifiers: its own ID or code, a system's code
  or external ID, a translated name;
- the object's system representations, translations and selected related objects in the same response;
- a contract that stays stable while the model and management API change.
- notice when reference data changes, pushed as webhooks or pulled from a feed.

The consumer API is read-only. It is not a thinner management API. Its responses are composed business
objects, and its contract is defined in the model, not in code.

## Reference implementation

This design comes from a consumer API already running in production. It is an API gateway policy set
over the source platform's reference data, and it is the functional baseline for this scope. The
policies are not stored in this repository (AGENTS.md). This section records what they do in engine
terms.

### XREF lookup

`GET /xref?query=…&type=…&codelist=…&domain=…&system=…&location=…`

- `query` is required. A comma-separated value is several terms, and an object's score is its best
  score across the terms.
- Candidates are master-data objects of every type, locations included.
- **Scoring for one term** (case-insensitive):

  | Where the term matches | Exact | Contains |
  | --- | ---: | ---: |
  | Object: global ID (master ID) | 1000 | — |
  | Object: value code, operator code | 500 each | 40 each |
  | Object: name, value name | 200 each | 30 each |
  | System value: name | 80 | 15 |
  | System value: external ID, system value name | 75 | 10 |
  | System value: system value code | 70 | 10 |
  | Translation: translated name | 60 | 12 |

  The object's own exact scores add up. Its "contains" scores count only when no exact score applied.
  A system value takes the first match in this order: exact name, code, external ID, value name, then
  contains on the same four. So a value whose code and external ID both match scores 70, not 75.
  Translations work the same way.
- **Promotion:** a matching system value or translation passes its score to the objects it relates to
  (highest score wins). When a system value relates to a location and to something else, only the
  location gets the score. This is what lets a location-only system value be found by external ID.
- **Filters**, applied after scoring:
  - `type`: object type.
  - `system`: keep only objects mapped by a system value of that system. Also limits which system
    values score and which appear in `systemVariants`.
  - `codelist` and `domain`: an ancestor's name or code.
  - `location`: a location matched by ID, name, code or value name. Keeps the location itself, objects
    available at it, and objects sharing a system value with it.
- **Cap:** results stop at `max(20, number of terms)`. `totalCount` is the number returned, not the
  number matched.

### Lists

One list per object type, on hierarchical routes such as `/domains/{domainId}/codelists`,
`/codelists/{codelist}/values` and `/stations/{stationId}/locations`.

- The parent segment accepts a global ID, an internal ID, or a name or code.
- Paging uses `page` and `pageSize`. `language` keeps only objects that have a translation in that
  language and limits `translations` to it. `locationId` filters by availability.
- The envelope is `page`, `pageSize`, `totalCount`, `returnedCount`, `items`.

### The shared object

XREF results and list items use the same object:

```json
{
  "objectType": "TimetableType",
  "masterId": "…", "code": "…", "name": "…", "valueName": "…",
  "sortOrder": 0, "isActive": true, "internalOnly": false,
  "validFrom": "", "validTo": "",
  "matchScore": 60,
  "systemVariants": [{ "system": "…", "value": "…", "valueCode": "…", "valueName": "…", "externalId": "…", "isActive": true }],
  "translations":   [{ "name": "…", "languageCode": "es", "languageName": "Spanish", "translatedName": "…", "translatedDescription": "…", "isActive": "true" }],
  "availableAt":    [{ "locationId": "…", "locationName": "…", "locationValueCode": "…", "locationValueName": "…" }],
  "duration":       [{ "durationId": "…", "durationCode": "…", "durationName": "…" }],
  "alternative":   [{ "objectType": "…", "masterId": "…", "code": "…", "name": "…" }],
  "path": "A/B/C", "parent": { "objectType": "…", "name": "…", "code": "…", "masterId": "…" },
  "hierarchy": ["A", "B", "C"]
}
```

`code` takes the first non-empty value of operator code, value code, codelist code, domain code and
station code. List items also carry `description`. Stations also carry `operatorCode` in XREF results.

### How flows call it

Integration flows call XREF through a shared gateway fragment. It sends the query with optional
filters, **takes the first result** and extracts one to three fields from it. It looks for the field at
the top level first, then in the nested arrays (limited to the requested system when the array has a
`system` field), then in `parent`. In practice XREF is the resolve operation: most flows pass a code or
external ID with `system` and use the top result.

### Behavior the engine does not carry over

Each item below is observed in the reference policies. The engine either fixes it or makes it explicit:

| Reference behavior | Engine behavior |
| --- | --- |
| Result cap of `max(20, terms)`; `totalCount` equals the returned count | Paged (ADR-030) with a real total. The default page size keeps the familiar 20 |
| Lists page by `page` number and report `returnedCount` | ADR-030 paging (C-D30): `position` jumps to a row, `startIndex` and the length of `items` give what `page` and `returnedCount` gave |
| A list's parent segment accepts a global ID, an internal ID, or a name or code | The parent is an object ID (C-D28); a name or code is matched by an `ancestor` parameter |
| Results with equal scores come back in an unspecified order (unstable sort), and flows take the first | Deterministic order: score, then object type, name, ID. `expect=one` returns an error instead of guessing when the top score is tied |
| Booleans and dates as strings (`"isActive": "true"` in translations, `validFrom: ""`) | Declared types kept: booleans, ISO dates, `null` |
| XREF omits `parent` for top-level objects; lists send a parent with empty strings | `parent` is always present; `null` when there is none |
| Lists build `hierarchy` by splitting `path` on `/`; XREF walks parents | Always walks parents, so names containing `/` stay one element |
| `operatorCode` exists only for one type; `description` only in lists | Fields come from the definition, not from type checks. XREF and lists return the same object |
| `alternative` is documented as an object or null but returned as an array | Single-valued relations project as an object or `null`, many-valued ones as an array (from relation cardinality) |
| The list `locationId` filter keeps items with no availability and compares a field that does not exist | Filter semantics are defined and tested |
| Cache invalidation by `X-Reset-Cache` and TTL | No manual reset: responses carry an ETag derived from the data and definition versions |

## Engine design

### Principle

The engine gets **no runtime knowledge** of locations, durations, alternatives, stations, system
values or translations (AGENTS.md). In this document they are examples from the reference deployment,
not requirements. Everything the reference policies hard-code (attribute and relation IDs, type
names, scoring weights, filter behavior, output field names) becomes a **consumer API definition** in
the model. The reference response must be reproducible from a definition alone. That is the
acceptance test for this scope (C8).

### Where definitions live

Consumer API definitions are a new top-level `consumerApis` section of the model document. They are
validated, compiled, installed and pinned like the rest of the model release. This reuses the existing
draft → validate → install lifecycle, gives every definition the model's precise path-and-reason
errors, and ensures a definition can never reference a type or relation the release lacks.

Each definition has its own `contractVersion`, separate from the model release version. A new model
release that changes a published definition's output must raise that definition's `contractVersion`.
Model validation compares definitions with the previously installed release and rejects an unmarked
breaking change (C-D2).

### The `apiKey`

`apiKey` is the `key` of one consumer API definition: the public, stable name of that API. It selects
which contract a request reads, in the route (`/api/consumer/{apiKey}/v{contractVersion}/…`), in a
subscription and in every event. It is **not a credential**: it grants nothing, is not secret, and
appears in URLs, logs and documentation like any other model key. Authentication is 0.12 work and
never travels in a URL ([Security](#security-012)).

- **Format:** a model key, lowercase letters, digits and hyphens, unique among the release's
  `consumerApis`.
- **Stability:** it names the API across all its contract versions. A breaking change raises
  `contractVersion` and keeps the `apiKey`; changing the `apiKey` creates a different API, and
  consumers of the old one get `404`.
- **Several per model:** a model may declare several definitions, each for a group of consumers, with
  its own exposed types, output shape, lists, events and contract version.

Examples:

| `apiKey` | What it is | Example request |
| --- | --- | --- |
| `rdm` | The reference deployment's API: XREF over codelist values, locations and system variants | `GET /api/consumer/rdm/v1/xref?query=CHF&system=SAP&expect=one` |
| `rdm` | The same API after a breaking change | `GET /api/consumer/rdm/v2/objects/7f3c…` |
| `locations` | A second definition on the same model exposing only locations and their availability, for a scheduling system | `GET /api/consumer/locations/v1/lists/station-locations?station=NORTH` |
| `catalogue` | A product catalogue model's API (COMPOSABLE_DOMAINS) | `GET /api/consumer/catalogue/v1/lists/products?category=tools&position=40` |

In a subscription the same key says which API's events to deliver: `"apiKey": "rdm"`.

### Definition shape

```jsonc
"consumerApis": [{
  "key": "rdm",
  "name": "RDM consumer API",
  "contractVersion": 1,

  // Public object type names and which types are exposed.
  "objectTypes": {
    "master-value": { "publicName": "CodelistValue" },
    "codelist":     { "publicName": "Codelist" },
    "location":     { "publicName": "Location" }
    // …
  },

  // The common object: fixed roles, output names chosen by the definition.
  "object": {
    "id":        { "output": "masterId",  "source": ["id"] },   // always the object ID (C-D24)
    "code":      { "output": "code",      "source": ["operator-code", "value-code", "codelist-code", "domain-code"] },
    "name":      { "output": "name",      "source": ["name"] },
    "active":    { "output": "isActive",  "source": ["active"], "default": true },
    "validFrom": { "output": "validFrom", "source": ["valid-from"] },
    "validTo":   { "output": "validTo",   "source": ["valid-to"] },
    "attributes": {
      "formerId":     { "source": ["master-id"] },   // a former system's ID, found with XREF
      "valueName":    { "source": ["value-name"] },
      "sortOrder":    { "source": ["sort-order"], "default": 0 },
      "internalOnly": { "source": ["internal-only"], "default": false },
      "description":  { "source": ["description"] }
    },
    "parent": { "output": "parent", "fields": ["objectType", "id", "code", "name"] },
    "path": "path", "hierarchy": "hierarchy"
  },

  // Named related-object blocks.
  "projections": {
    "systemVariants": {
      "from": { "relation": "system-value-maps-to-master", "direction": "incoming" },
      "fields": {
        "system":     "ancestor:system.name",
        "value":      "name",
        "valueCode":  "value-code",
        "valueName":  "value-name",
        "externalId": "external-id",
        "isActive":   "active"
      }
    },
    "translations": {
      "from": { "relation": "object-has-translation", "direction": "outgoing" },
      "fields": {
        "languageCode":          "ancestor:language.language-code",
        "languageName":          "ancestor:language.name",
        "translatedName":        "translated-name",
        "translatedDescription": "translated-description",
        "isActive":              "active"
      }
    },
    "availableAt": {
      "from": { "relation": "available-at-location", "direction": "outgoing" },
      "fields": { "locationId": "master-id", "locationName": "name", "locationValueCode": "value-code", "locationValueName": "value-name" }
    }
  },

  // XREF matching.
  "match": {
    "own": [
      { "field": "master-id",  "exact": 1000 },
      { "field": "value-code", "exact": 500, "contains": 40 },
      { "field": "operator-code", "exact": 500, "contains": 40 },
      { "field": "name",       "exact": 200, "contains": 30 },
      { "field": "value-name", "exact": 200, "contains": 30 }
    ],
    "promoted": [
      { "projection": "systemVariants", "firstMatch": [
          { "field": "name", "exact": 80 }, { "field": "value-code", "exact": 70 },
          { "field": "external-id", "exact": 75 }, { "field": "value-name", "exact": 75 },
          { "field": "name", "contains": 15 }, { "field": "value-code", "contains": 10 },
          { "field": "external-id", "contains": 10 }, { "field": "value-name", "contains": 10 } ],
        "preferTargetTypes": ["location"] },
      { "projection": "translations", "firstMatch": [
          { "field": "translated-name", "exact": 60 }, { "field": "translated-name", "contains": 12 } ] }
    ]
  },

  // Request parameters, each bound to a generic filter kind.
  "parameters": {
    "type":     { "kind": "objectType" },
    "system":   { "kind": "projection", "projection": "systemVariants", "matchFields": ["ancestor:system.name", "ancestor:system.system-code"],
                  "scoresFrom": true, "requireMatch": true, "targetable": true },
    "codelist": { "kind": "ancestor", "objectTypes": ["codelist"], "matchFields": ["name", "codelist-code"] },
    "domain":   { "kind": "ancestor", "objectTypes": ["domain"], "matchFields": ["name", "domain-code"] },
    "location": { "kind": "related", "objectTypes": ["location"], "matchFields": ["master-id", "name", "value-code", "value-name"],
                  "via": ["availableAt", "self", "sharedProjection:systemVariants"] },
    "language": { "kind": "projection", "projection": "translations", "matchFields": ["ancestor:language.language-code"], "requireMatch": true }
  },

  // Lists.
  "lists": [
    { "key": "codelists", "objectType": "codelist", "parentParameter": { "name": "domain", "objectTypes": ["domain"] } },
    { "key": "values",    "objectType": "master-value", "parentParameter": { "name": "codelist", "objectTypes": ["codelist"] } },
    { "key": "all-values", "objectType": "master-value" }   // no parent: every object of the type
    // …
  ]
}]
```

The example is the reference deployment's definition. Every key, projection and parameter name in it
is that deployment's choice, not something the engine requires. Keys missing from `rdm-starter.json`
(`available-at-location`, `location`, `operator-code`, `internal-only`) come from a model that extends the
starter, as the source deployment's does.

The engine supplies only these parameter kinds. A definition names its parameters and binds each one
to a kind:

| Kind | Effect |
| --- | --- |
| `objectType` | Keeps objects of the named public types |
| `ancestor` | Keeps objects that have an ancestor of the listed types matching on `matchFields` |
| `related` | Keeps objects linked to a matching object through the `via` routes: a projection, the object itself, or a shared projection (both objects relate to the same projected object) |
| `projection` | Limits a projection to the items that match on `matchFields`. `requireMatch` also drops objects left with no matching item. `scoresFrom` means only the matching items pass scores on to their objects |

In the example, `system` and `language` are both `projection` parameters. The engine does not treat
them as a system or a language.

Rules the validator enforces:

- **Sources:** every `source`, `field` and `ancestor:<type>.<field>` reference resolves in the release.
  A source list means "first non-empty value", which replaces the reference `code` fallback chain.
- **Scalar values** keep their declared attribute type; `default` must match that type.
- **Projection shape:** a projection is an object or `null` when the relation, in that direction,
  allows at most one related object, and an array otherwise. This is derived, never declared, so a
  model cardinality change becomes a contract change the validator can see.
- **Match fields** must be `searchable` or explicitly listed as identifiers; weights are positive
  integers.
- **Parameter names** are unique per definition and cannot shadow reserved names (`query`, `expect`,
  `pageSize`, `cursor`, `position`, `from`, `seek`, `includeTotal`, `publication`, `asOf`,
  `workspace`, `ref`, `id`) or start with `to.`.
- **List order (C3):** a list's optional `sortBy` names a scalar attribute (not JSON) its type binds,
  refused otherwise at `/consumerApis/<key>/lists/<list>/sortBy`; changing it is a breaking change.
- **Crosswalk targets:** a `projection` parameter may declare `"targetable": true`, which enables
  `to.{parameter}` on reads (see Crosswalk). Only a `projection` parameter can be targetable.
- **Lists without a parent** omit `parentParameter` and list every object of the type.

_Delivered in C1 (2026-09-30), with these rules settled on the way:_

- **Keys:** a definition's `key` (the `apiKey`) and each list `key` use lowercase letters, digits and
  hyphens, since they appear in URLs; public type names are unique within a definition.
- **Source types (C-D19):** a field's sources share one value type (`text` and `longText` count as
  one), which is the field's output type; a mixed list is refused at the field's `source`.
- **Identity:** the `id` role's source is the built-in `id`, the object ID (narrowed in C2, C-D24);
  another source is refused at `/consumerApis/<key>/object/id/source`. A former system's ID is
  published as an ordinary attribute field and found with XREF. A migration that wants to keep a
  former ID as the object ID assigns it as the object ID when it creates the record (a UUID).
- **Output names** are unique across roles, attributes, `parent`, `path`, `hierarchy` and projections,
  and `objectType`, `matchScore` and `target` are reserved for the engine. A `parent` field `code`
  needs the object's `code` role.
- **Match fields (C-D20):** a match rule, and an `ancestor` or `related` parameter's `matchFields`,
  read `name`, `id` or an attribute of the relevant types that is `searchable` or `unique`; a
  `projection` parameter's `matchFields` are fields of the projection, `ancestor:` references included.
- **Routes:** a projection's relation must be bound, in its direction, to at least one exposed type; an
  `ancestor` parameter's types must be ancestors of an exposed type; a `related` parameter's `via` is
  `self`, a projection or `sharedProjection:<projection>`; a list's parent types must be able to
  contain its type. A list's parent parameter may share a definition parameter's name.
- **Not yet:** `events` is refused as an unknown field until C9.

### Endpoints

```text
GET /api/consumer/{apiKey}/v{contractVersion}/xref?query=…&{parameters}&expect=one|any&pageSize=…
GET /api/consumer/{apiKey}/v{contractVersion}/objects/{id}?{parameters}
GET /api/consumer/{apiKey}/v{contractVersion}/lists/{listKey}?{parentParameter}=…&{parameters}&position=…&pageSize=…
GET /api/consumer/{apiKey}/v{contractVersion}/openapi.json
POST /api/consumer/{apiKey}/v{contractVersion}/resolve
GET /api/consumer/{apiKey}/v{contractVersion}/publications?pageSize=…
GET /api/consumer
```

- **XREF** keeps the reference request and response shape, with `results`, `query` and `totalCount`
  plus the paging fields of ADR-030. `expect=one` returns the single top result, `404` when nothing
  matched, and `409 AMBIGUOUS_MATCH` naming the tied candidates when the top score is shared. Flows
  that resolve a value use it in place of "take the first result".
- **Get by ID** returns one object in the same shape, found by its object ID (C-D24). _Delivered in
  C2 (2026-10-04):_ the answer is the bare shared object; an unknown or deleted record, one in another
  workspace or one of a type the definition does not expose is `404 OBJECT_NOT_FOUND`. Data is read
  live from the active release's definition (C-D6; `publication` arrives in C6). `workspace` selects
  the workspace, defaulting to the deployment's default; an unknown or retired one is
  `404 WORKSPACE_NOT_FOUND`, and every response names the workspace in `RDM-Workspace` (C-D23).
  `parent` is an object or `null`; its `objectType` is `null` when its type is not exposed (C-D22).
  `hierarchy` and `path` hold the ancestors from the top down, without the object (C-D21). A field
  with no value from any source takes its `default`, then `null`; empty text is no value (C-D26).
  Projection arrays are ordered by the related record's name, then ID.
- **Lists** page as the management lists do (ADR-030, C-D30): cursors both ways with `anchor`,
  `position`, `from=end`, `seek` and `includeTotal`, with `pageSize` 1–100 (default 20). The envelope
  is `items`, `workspace`, `pageSize`, `nextCursor`, `prevCursor`, `anchor`, `totalCount` and
  `startIndex` (the last two `null` without `includeTotal=true`). The parent parameter takes object
  IDs only (C-D28) and keeps the records of the list's type anywhere below them (C-D27); without it a
  list holds every object of its type. The order is the list's optional `sortBy` attribute (records
  without a value last), then name, then creation order (C-D29); pinned to a publication (C6), a list
  without a parent is a consistent full extract of that type. _Delivered in C3 (2026-10-04)_, with
  every definition parameter applying to lists and to get by ID (C-D31).
- **Unknown parameters** are rejected with `400 UNKNOWN_PARAMETER` naming them. Unknown `apiKey`,
  `listKey` or `contractVersion` return `404` (`CONSUMER_API_NOT_FOUND`, `CONTRACT_VERSION_NOT_FOUND`
  naming the installed version). A name the API knows that a route does not apply
  (a paging name on get by ID, a list's parent parameter on get by ID or another list) is refused with
  `400 PARAMETER_NOT_SUPPORTED` (C3).
- **Generated OpenAPI:** each definition generates its own OpenAPI document, so integrators get a
  typed contract per API.
- **Consistency:** reads use live data by default. `publication={publicationId}` reads a
  publication, so a flow or extract can pin one consistent snapshot; `publication=latest` reads the
  workspace's newest publication, and the response names the publication it resolved to. Responses
  carry `ETag: "{dataVersion}:{contractVersion}"` and honor `If-None-Match`.

#### Batch resolve

`POST …/resolve` resolves many values in one call, so a flow translating a file of codes does not make
one XREF request per row. It is a read: POST only carries the list, and it changes nothing.

```jsonc
{
  "defaults": { "system": "SAP", "codelist": "Currency" },       // parameters for every item
  "items": [
    { "ref": "row-1", "query": "CHF" },
    { "ref": "row-2", "query": "EUR", "to.system": "Oracle" },    // crosswalk, see below
    { "ref": "row-3", "id": "7f3c…" }                             // by ID
  ]
}
```

- Each item is resolved exactly as `xref?expect=one` (by `query`) or get by ID (by `id`), with its own
  parameters over `defaults`. Scoring, filters and tie rules are the XREF ones.
- Each outcome carries `index`, `ref` and a `status`: `found` with the shared object, `not_found`,
  `ambiguous` with the tied candidates' identities, or `rejected` with an error (an unknown parameter,
  an unresolvable `to.` target). The same envelope as the integration API's item outcomes
  ([INTEGRATION_API P2](INTEGRATION_API.md#p2-items-and-outcomes)), with the statuses of a read.
- The request's `publication` and `asOf` apply to every item. The batch maximum is a setting (C-D13);
  over it the request is `413` and nothing is resolved. Outcomes come back in item order, unpaged,
  because the batch is bounded.

#### Crosswalk

"Code X in system A: what is it in system B?" is a resolve whose output is narrowed to the target
representation. On XREF, get by ID, lists and batch resolve, `to.{parameter}` names a targetable
`projection` parameter and a value:

```text
GET …/xref?query=CHF&system=SAP&to.system=Oracle&expect=one
```

- The plain parameter (`system=SAP`) still decides matching and scoring. `to.system=Oracle` limits
  that projection in the output to the items matching `Oracle` and adds them as `target`.
- With `expect=one` (and in batch resolve) the target must also be unique: no matching item answers
  `404 target_not_found`, several answer `409 ambiguous_target`, each naming the object found.
- The engine treats neither systems nor translations specially: any targetable projection parameter
  crosswalks, so the same form returns a value's Spanish translation with `to.language=es`.

#### Business dates: `asOf`

`asOf=YYYY-MM-DD` applies to XREF, get by ID, lists and batch resolve. It keeps only objects whose
model-declared effective period contains that date (Base 0.9 plan D6), across every page of the
request. It never infers validity from an arbitrary date field:

- a list or get by ID of a type with no declared period answers `400 AS_OF_NOT_SUPPORTED`, naming
  the type (SC-11);
- XREF across several types applies `asOf` to the types that declare a period and reports them in
  `asOfApplied`; the other types are returned unfiltered (C-D14).

Business validity (`asOf`), publication (`publication`) and change time (events) stay separate
parameters and may be combined.

#### Publications

`GET …/publications` lists the publications of the workspace the API reads, newest first, paged
(ADR-030). Each has its `id`, `publishedAt` and `eventSequence`: the event position current when it
was published, so a consumer can extract a list pinned to it and then follow events from that
position (C-D15). It lets a consumer that cannot call the management API find a snapshot to pin.

#### API index

`GET /api/consumer` lists the installed definitions, paged: `apiKey`, `name`, `contractVersion` and the
URL of each OpenAPI document. Clients discover the APIs from it, and the API reference page (Base 0.9
Track D) builds its list of sources from it.

The existing gateway can stay in front and map the reference routes (`/xref`,
`/stations/{stationId}/locations`, …) onto these endpoints, so current consumers move without changes
(C-D5).

### Read index

The reference answers in about 100 ms only from its cache; a miss reloads the whole dataset. The
engine cannot score every object and join every projection per request. Each definition gets a
**consumer index** per workspace:

- a match table of (object, source field or promoted-from object, normalized value, weights), so an
  exact lookup is an index seek and "contains" runs over one narrow table;
- a precomputed hierarchy path per object;
- updated in the same transaction as the live write that changes an indexed value or relation, like
  `snapshot_attribute_values` in 0.8 S2, and rebuilt on definition or model install.

Projections for a result page are loaded in one batched query per projection, not per object. Budgets
are set against the 0.8 Track S volume fixture (C8).

## Change events and webhooks

Consumers learn that reference data changed without polling. This is the consumer-facing part of the
0.9 "ordered change feed and retryable webhooks" item. Webhooks and a pull feed of the same events
deliver them. The engine only sends signed HTTP requests. Whatever a receiver does next (an export
then an import, a cache refresh, a downstream sync) is up to the receiver.

### What counts as a change

Only data changes, as a consumer sees them:

| Source | Events |
| --- | --- |
| Live create, update or delete of an object, attribute value or relation | Yes |
| Change set publication | Yes, one event per affected consumer object, all naming the same publication |
| Bulk or import job | Yes, one event per affected consumer object, all naming the job |
| Change set (change set) edits, validation, discard | No |
| Model release install, workspace administration | No |

An event is about a **consumer object**, not a raw record. A change to a projected record changes the
object that projects it. For example, a system value's external ID edited in a model like the
reference makes an `updated` event for the master value whose `systemVariants` includes it. Changes
to records no definition exposes or projects make no event.

### Event definitions (model)

Each consumer API definition declares its events next to its object, projections and parameters:

```jsonc
"events": [{
  "key": "reference-data-changed",
  "objectTypes": ["master-value", "codelist", "location"],
  "changes": ["created", "updated", "deleted"],
  "watch": {
    "fields": ["id", "code", "name", "active", "validFrom", "validTo", "valueName"],
    "projections": ["systemVariants", "translations"]
  }
}]
```

- `objectTypes` must be exposed by the definition; `changes` is any of `created`, `updated`, `deleted`.
- `watch` limits `updated`. Only changes to the listed output fields or projections count, so edits
  to unexposed attributes make no event. When `watch` is omitted, any change to the object's output
  counts.
- Events are part of the contract: removing an event, or narrowing its types or changes, needs a new
  `contractVersion` (C-D2).

### Subscriptions (runtime, not model)

Where events go is deployment data: URLs and secrets differ by environment and must not enter an
immutable, portable model release. An administrative API manages subscriptions:

```text
POST   /api/v1/consumer-subscriptions
GET    /api/v1/consumer-subscriptions?apiKey=…&cursor=…
GET    /api/v1/consumer-subscriptions/{id}
PATCH  /api/v1/consumer-subscriptions/{id}          (optimistic concurrency, like other updates)
POST   /api/v1/consumer-subscriptions/{id}/rotate-secret      (0.12)
POST   /api/v1/consumer-subscriptions/{id}/resume
DELETE /api/v1/consumer-subscriptions/{id}
```

```jsonc
{
  "apiKey": "rdm",
  "workspaceKey": "main",
  "events": ["reference-data-changed"],
  "filters": { "type": "Location", "codelist": "Country" },
  "url": "https://integration.example.com/hooks/rdm",
  "mode": "perChange",                // or "coalesced"
  "debounceSeconds": 60,              // coalesced only
  "enabled": true
}
```

- **Filters** reuse the definition's parameters and kinds (`objectType`, `ancestor`, `projection`,
  `related`), so a subscription scopes exactly as an XREF or list call would. Filters apply to the
  object's state after the change, and to its last state for a deletion.
- **The signing key** (0.12) is generated by the engine, returned once on create and rotate, and stored
  encrypted. 0.9 subscriptions have none.
- **Target hosts** must match the deployment allowlist (`CONSUMER_WEBHOOK_ALLOWED_HOSTS`) and use
  HTTPS, except allowlisted local hosts in development. Subscriptions cannot point at arbitrary
  internal addresses.
- **After a model change**, a subscription whose events or filters no longer exist in the installed
  definition is suspended with a machine-readable reason. It is never silently rewritten.

### Delivery

- **Per-change mode:** one POST carries a batch of up to 100 events in position order, so a bulk job
  or a large publication becomes a few requests, not thousands.
- **Coalesced mode:** one POST says "this scope changed" after `debounceSeconds` without new
  matching events, or after at most 10 minutes of continuous change. This fits "run an export when
  data changes".
- **Ordering:** each subscription delivers in feed-position order (INTEGRATION_API F3). A batch goes out only after the
  previous one is acknowledged.
- **Acknowledgement and retry:** any `2xx` acknowledges. Anything else, or a timeout (10 s), is
  retried with exponential backoff and jitter for up to 24 hours. After that the subscription is
  **suspended**. `resume` continues from the first unacknowledged event; nothing is skipped.
- **At-least-once:** receivers deduplicate by `eventId`. The event `position` tells them whether they
  are behind.
- **Headers:** `RDM-Delivery-Id` and `RDM-Timestamp`. From 0.12 also
  `RDM-Signature: sha256=<HMAC of "{timestamp}.{body}">`; receivers then verify it and reject stale
  timestamps to prevent replay. Adding the header is additive: a 0.9 receiver keeps working and starts
  verifying when it is ready (C-D12).

Per-change body:

```json
{
  "deliveryId": "…",
  "subscriptionId": "…",
  "apiKey": "rdm", "contractVersion": 1, "workspaceKey": "main",
  "events": [{
    "eventId": "…", "position": 184223, "occurredAt": "2026-09-26T10:14:03Z",
    "event": "reference-data-changed", "change": "updated",
    "objectType": "TimetableType", "id": "…", "code": "…", "name": "…",
    "changed": ["systemVariants"],
    "cause": { "kind": "publication", "id": "…" }
  }]
}
```

Coalesced body:

```json
{
  "deliveryId": "…", "subscriptionId": "…",
  "apiKey": "rdm", "contractVersion": 1, "workspaceKey": "main",
  "event": "reference-data-changed",
  "fromPosition": 184100, "toPosition": 184223, "eventCount": 124,
  "objectTypes": ["TimetableType", "Location"],
  "occurredFrom": "…", "occurredTo": "…"
}
```

Events carry the object's identity (`id`, `code`, `name`) and which watched outputs changed, not the
full object. A receiver that needs the object calls get-by-ID or a list. This keeps event creation
cheap and avoids delivering a snapshot that is already stale (C-D7).

### Pull feed

```text
GET /api/consumer/{apiKey}/v{contractVersion}/events?event=…&after={position}&cursor=…&pageSize=…&{parameters}
```

The same events, paged in position order, filtered with the definition's parameters. It serves
receivers that prefer polling, catch-up after downtime or a suspension, and verification. Events are
retained for a configurable period, 30 days by default (C-D9). A request for a position older than
retention answers `410 EVENTS_EXPIRED`: the receiver re-syncs by reading its lists pinned to a
publication and resuming the feed from that publication's `eventSequence` (C-D15).

### How events are produced

The audit log (`audit_events`) is already written in the same transaction as every data change. It
serves as the outbox. Every entry that changes live data carries a per-workspace feed position
assigned in commit order (Base 0.9 D5, INTEGRATION_API F3), and a publish writes one entry per record
it applies (D15). An event deriver reads new entries in position order after commit, evaluates them
against the installed definitions and appends consumer events (C-D8):

- a rolled-back write leaves no audit entry, so no event is produced;
- a write never waits on event evaluation or delivery;
- mapping a projected record back to its owning objects uses the relation ends stored in the audit
  entry, so it also works when the relation itself was deleted.

The deriver and the dispatcher run in the application process while it is single-node. Multi-node
coordination is 0.11 work.
