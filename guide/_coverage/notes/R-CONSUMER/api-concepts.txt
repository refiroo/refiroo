988: ## Change sets and publications — current API and accepted targets
989: 
990: A workspace has live data, change sets and publications ([ADR-031](DECISIONS.md#adr-031--workspace-terminology-and-deployment-capability-boundaries)).
991: A **change set** is an optional group of data changes published together; **publishing** it creates
992: **Publication N**, an immutable snapshot, and makes its changes live. **Withdrawing** a publication
993: removes its current designation. Model drafts and model releases are a separate lifecycle
994: ([model endpoints](#model-endpoints)).
995: 
996: ADR-024 replaces the rejected WP4 object-lifecycle surface. Object-draft, object-revision, activation
997: and object-retirement endpoints from WP4 are migration history, not public contracts; clients and UI
998: must not call them. WP6 implemented the publication storage and corrective migration, WP7 restored the
999: canonical record resources over that storage, and WP8 completed and tested the lifecycle surface
1000: below. ADR-026 restored direct live writes; ADR-027 records the remaining WP8.1 corrections; Base 0.8
1001: W2 gave every route, field and error code its ADR-031 name.
1002: 
1003: **Route shape.** Collections stay nested under their workspace
1004: (`/workspaces/{workspaceKey}/change-sets`, `/workspaces/{workspaceKey}/publications`); a single change
1005: set or publication is addressed flat by its global ID (`/change-sets/{changeSetId}`,
1006: `/publications/{publicationId}`), including its actions. New endpoints follow the same rule.
1007: 
1008: - `GET|POST /api/v1/workspaces/{workspaceKey}/change-sets` lists cursor-paged change sets or creates
1009:   one from an explicit source. `source: "currentLive"` captures a private immutable base from the
1010:   current live graph; it includes typed fields, parent/typed containment edges, independent relations,
1011:   record versions and the selected model identity, and works when no publication exists. It creates
1012:   no publication. `source: "publication"` requires `derivedFromPublicationId` and retains the selected
1013:   immutable publication as the source. For compatibility, omitted `source` keeps the old meaning: a
1014:   supplied `derivedFromPublicationId` derives from that publication and its absence creates the
1015:   documented empty development/bootstrap root. `currentLive` rejects a publication ID and
1016:   `publication` rejects its absence with request validation errors; clients must not infer current
1017:   data from the last publication.
1018: - `GET|PATCH|DELETE /api/v1/change-sets/{changeSetId}` reads, names or discards a change set. PATCH
1019:   and DELETE claim `expectedVersion`. An unknown ID returns `404 CHANGE_SET_NOT_FOUND`.
1020: - The existing canonical object, attribute, containment and relation resources retain their paths,
1021:   request/response shapes and CRUD semantics. `workspaceKey` selects live data, `changeSetId` selects
1022:   the effective content of a change set for reads and writes, and `publicationId` selects an
1023:   immutable publication. Change-set and publication contexts are mutually exclusive. Writes go into a
1024:   change set only when the caller supplies `changeSetId` (with `expectedChangeSetVersion`); change-set
1025:   updates and deletes also claim the existing record's `expectedVersion`, while a create has no prior
1026:   record version. Without a change set, mutations target live data; updates/deletes claim the record
1027:   `expectedVersion`, while creation has no previous record version; an existing object or relation
1028:   supplies its workspace context. Only a live object create requires `workspaceKey`. This execution
1029:   context is not a second public CRUD dialect: there are no `/change-sets/{changeSetId}/objects` or
1030:   `/change-sets/{changeSetId}/relations` resources. Live writes never change a publication.
1031: - Change-set creation accepts optional `modelReleaseId` (installed public UUID). Current-live creation
1032:   captures the active data and versions while pinning the chosen release; the complete copied graph
1033:   must fit before creation commits. Creation from a publication retains that publication's pin and
1034:   refuses a simultaneous release selection. Change-set responses include `modelReleaseId`,
1035:   `modelReleaseKey` and `modelReleaseVersion`.
1036: - `PATCH /api/v1/change-sets/{changeSetId}/model-release` accepts `modelReleaseId` and
1037:   `expectedChangeSetVersion`. It claims the change-set version, checks the complete effective graph
1038:   (base plus authored content minus tombstones) under the target, then changes only that pin. Success
1039:   increments the change-set version and audits old/new public release identities. A valid request
1040:   selecting the current pin is a no-op. Stale claims return `409 CHANGE_SET_VERSION_CONFLICT`.
1041:   Declared attribute type changes for stored effective object/relation values require conversion,
1042:   even if a target normalizer could accept the old value. Populated containment also retains its
1043:   source model semantics; changing those requires conversion. Missing required fields are not
1044:   defaulted during compatibility checks. Incompatible content returns
1045:   `409 CHANGE_SET_CONTENT_INCOMPATIBLE` with `details.diagnostics` (at most 20), `diagnosticCount` and
1046:   `diagnosticsTruncated`; refusal leaves content, pin and version unchanged. Uniqueness conflict ID
1047:   previews are also bounded to 20 with exact count/truncation metadata. No conversion is performed.
1048:   Missing, unsupported and invalid targets use `PINNED_MODEL_UNAVAILABLE`,
1049:   `UNSUPPORTED_PINNED_MODEL_SCHEMA` and `PINNED_MODEL_INVALID` respectively.
1050: - `/model` and model metadata reads accept `changeSetId` or `publicationId` and resolve that context's
1051:   installed model. Metadata cursors are bound to the release identity. Change-set record reads, writes
1052:   and graph validation use the change set's pin even when it differs from active; agreement with the
1053:   active release is a separate requirement for publishing. Discard does not require model agreement.
1054: - `POST /api/v1/change-sets/{changeSetId}/validation` validates the complete effective graph without
1055:   publishing. It answers `200` with `{ "valid": true|false, "diagnostics": [...] }`: an invalid graph
1056:   is `valid: false` with a diagnostic per problem, naming the records, not an error response. `POST /api/v1/change-sets/{changeSetId}/publication` publishes it and requires
1057:   `expectedChangeSetVersion` and nullable `expectedActivePublicationId`. Stored read-only values,
1058:   including model defaults, are valid publication content and are checked for their declared types and
1059:   constraints; ordinary writes and attribute deletion still enforce the binding's read-only
1060:   restriction.
1061: - `GET /api/v1/change-sets/{changeSetId}/object-changes` and
1062:   `GET /api/v1/change-sets/{changeSetId}/relation-changes` (Base 0.8 P2a) list only what the change set
1063:   changes, one entry per record or relation it touched, read against its **source** (its current-live
1064:   base or publication; nothing for an empty root). They are read-only entries about records, not a
1065:   record dialect. Each entry has a `kind` (D31): `added` (no source row), `changed` (a source row) or
1066:   `removed` (deleted, with a source row). A record created and deleted inside the change set is left
1067:   out, as publishing skips it. `before` is the record as the source holds it and `after` as the change
1068:   set does; each is `null` where the kind has none. *Before* is not current live: whether live moved
1069:   since is what validation and publishing report (`VERSION_CONFLICT`).
1070:   - An object entry carries `kind`, `objectId`, `objectTypeKey`, `applicationKey`, `before`/`after`
1071:     (`objectTypeKey`, `name`, `parentObjectId`, typed `attributes` in the object read's shape,
1072:     `version`), `changedFields` and `path`: where the change set puts an added or changed record, or
1073:     where the source held a removed one. `changedFields` names what differs between the sides
1074:     (`objectType` when a type change made them differ, Base 0.8 C1; then `name`, `parent`, then
1075:     attribute keys in binding order); a missing side holds nothing, so an added or
1076:     removed record names every field it holds. A `changed` entry can name none — edited back to its
1077:     source values — and is still listed: its version advanced and publishing claims it against live.
1078:     A move is `changed` with `parent`, and carries `beforePath`: where the source held the record
1079:     (root first, ending with the record); `beforePath` is `null` on every other entry (Base 0.8 P2b).
1080:   - A relation entry carries `kind`, `relationId`, `relationTypeKey`, `containment`, `fromObject` and
1081:     `toObject` (`objectId`, `objectTypeKey`, `name`: as the change set holds the record, or the source
1082:     for a removed end), `before`/`after` (`attributes`, `version`) and `changedFields` (attribute
1083:     keys). `containment` marks an engine-maintained parent edge: its type is one of the `to` end
1084:     type's `parentRelationTypeKeys` under the change set's model. The lists include these edges so an
1085:     integration sees every row that publishes (D32); a move lists one removed and one added edge.
1086:   - Filters: repeatable `kind`; repeatable `objectTypeKey` on objects; repeatable `relationTypeKey` and
1087:     `containment` (`true` only parent edges, `false` none; both when omitted) on relations. A type key
1088:     not in the change set's model returns `422 UNKNOWN_OBJECT_TYPE` or `422 UNKNOWN_RELATION_TYPE`
1089:     with `details.path` and `details.key`; an unknown kind is a request validation error. There is no
1090:     search.
1091:   - Objects list by (`objectTypeKey`, name, `objectId`), the change set's name (a removed record keeps
1092:     its name); relations by (`relationTypeKey`, `relationId`). Both page as every collection does
1093:     ([Collection paging](#collection-paging)), `pageSize` 1–500 (default 100); cursors are bound to
1094:     the change set and filters. An unknown change set returns `404 CHANGE_SET_NOT_FOUND`. There is no
1095:     publication context: what a publication changed against its predecessor is the 0.9 change feed.
1096: - `GET /api/v1/workspaces/{workspaceKey}/publications` and `GET /api/v1/publications/{publicationId}`
1097:   list and read publications. A publication carries `publicationNumber`, its `status` (`active` while
1098:   it is the workspace's current publication, otherwise `withdrawn`), `publishedAt`, `withdrawnAt`,
1099:   `derivedFromPublicationId`, `supersedesPublicationId` and its `modelReleaseId`, `modelReleaseKey`
1100:   and `modelReleaseVersion`, so a client can show "Publication 12 · model 0.8.0 · 3 Sep 2026".
1101:   `feedPosition` is the position of its `published` entry in the
1102:   [change feed](#change-feed-base-09-f1-f2): live data at that position is the publication, so a feed
1103:   reader re-reads it and follows on from there. It is `null` for a publication made before the feed
1104:   existed.
1105:   `publicationNumber` is a per-workspace counter that never restarts, not a version. The list is
1106:   newest first by publication number with the public UUID as a unique descending tie-breaker. Its
1107:   cursor is bound to the workspace and descending sort; an ascending, malformed or differently scoped
1108:   cursor returns `422 INVALID_CURSOR` with `Publication cursor is invalid`. Pages contain 1–500 items
1109:   and exact retry is deterministic. An unknown ID returns `404 PUBLICATION_NOT_FOUND`.
1110: - `POST /api/v1/publications/{publicationId}/withdrawal` withdraws the workspace's current
1111:   publication: its status becomes `withdrawn` and the workspace no longer has a current publication.
1112:   The path ID is the concurrency claim, so a publication that is no longer current returns
1113:   `409 WORKSPACE_ACTIVE_PUBLICATION_CONFLICT`. It retains the live records and every publication; it
1114:   does not retire the workspace or change any individual record. A retired workspace refuses it with
1115:   `409 WORKSPACE_RETIRED`.
1116: 
1117: A publication snapshots one graph: objects, typed attributes, containment (both parent projection
1118: and typed edge), required ownership relations and independent relations. Stable object and relation
1119: UUIDs remain integration identities but have no lifecycle state. Change sets pin `modelReleaseId`;
1120: publications record the `modelReleaseId` they were published under. Publishing against another
1121: resolved model returns `409 CHANGE_SET_MODEL_RELEASE_CONFLICT` and never rebases implicitly.
1122: Publishing delta-merges the change set onto the current live content and snapshots the merged graph,
1123: so a change set started from an earlier publication preserves newer live records it never touched
1124: (ADR-026). Conflicts are `CHANGE_SET_VERSION_CONFLICT`, `WORKSPACE_ACTIVE_PUBLICATION_CONFLICT`,
1125: `CHANGE_SET_MODEL_RELEASE_CONFLICT`, and `VERSION_CONFLICT` — publishing reports every per-record merge
1126: divergence under `409 VERSION_CONFLICT` with `details.conflicts` (`kind`, `id`, `code`
1127: `VERSION_MISMATCH`/`ID_COLLISION`/`DUPLICATE_EDGE`, expected/actual version) — plus
1128: `422 WORKSPACE_GRAPH_INVALID` when the merged graph fails whole-graph validation. Publishing also
1129: compares complete source/live relation identities and versions for exact directional mutable binding
1130: sets touched by the change set. A divergent set adds a diagnostic with `kind: "mapping-set"`,
1131: `code: "MAPPING_SET_CHANGED"`, `id`/`anchorObjectId`, physical binding type keys, `direction`,
1132: expected/actual target counts and a recovery message. At most 20 mapping-set diagnostics are
1133: returned; `details.mappingSetConflictCount` gives the exact total and
1134: `details.mappingSetConflictsTruncated` indicates omitted mapping-set diagnostics. No graph is applied,
1135: no publication is created, and the change set remains available. Review current live mappings and
1136: reapply intended changes in a new current-live change set before publishing; validating the unchanged
1137: conflicting change set does not resolve the conflict. Containment/ownership use their existing merge
1138: rules. Identical source/live edge identities and surviving edge versions count as the same graph, even
1139: if an intervening addition was later removed. Change-set and publication collection cursors bind
1140: their selected context identity and query filters; malformed/mismatched tokens return
1141: `422 INVALID_CURSOR`. Live collection cursors bind the effective live workspace and query filters.
1142: Cursor tokens do not bind a model or publication ID unless that context is itself selected.
1143: 
1144: Current-live capture reads the graph from one database snapshot (REPEATABLE READ), so live writes
1145: committing meanwhile are not mixed into it, and holds share locks on the workspace and runtime-state
1146: rows, so neither a retirement nor a model activation commits while it runs. It compares the request's
1147: captured active release with `model_runtime_state`, separately from the selected change-set pin. A
1148: changed active selection, or a workspace or runtime-state row changed after the snapshot began,
1149: returns `409 CHANGE_SET_SNAPSHOT_RETRY` with an actionable retry message and saves nothing
1150: (0.9.0-alpha.1; `change_set_snapshot_unsupported` is no longer returned). The private base is deleted
1151: with its change set on discard or publish and is never a publication or part of publication lineage.
1152: 
1153: Change-set responses return `source: "currentLive"`, `"publication"` or `"empty"`; `empty` reports a
1154: compatible legacy/bootstrap change set and is not a normal source choice. The private base ID is not
1155: exposed.
1156: 
1157: Change-set and publication reads resolve their pinned supported model before field/filter metadata,
1158: typed responses or relationship expansion. Missing, corrupt or unsupported pins return structured
1159: errors and never fall back to the active model. Supplying `workspaceKey` with a change set or
1160: publication must match that context; change-set and publication IDs remain mutually exclusive. Live
1161: writes continue to resolve the active model, while change-set writes validate and respond using the
1162: change set's pinned model.
1163: 
1164: These refusals use the normal error envelope. A context mismatch is `422` with
1165: `{"error":{"code":"WORKSPACE_CONTEXT_MISMATCH","message":"workspaceKey does not match the selected context","details":{"workspaceKey":"...","contextWorkspaceKey":"..."}}}`.
1166: A missing pinned release is `409` with code `PINNED_MODEL_UNAVAILABLE`; an invalid pinned document is
1167: `409` with `PINNED_MODEL_INVALID` and its diagnostics; and an unsupported schema is `409` with
1168: `UNSUPPORTED_PINNED_MODEL_SCHEMA`, including `modelReleaseId`, `schemaVersion`, and
1169: `supportedSchemaVersions: ["0.5", "0.6"]` in details.

2152: ## Batches and jobs (Base 0.9 B1, B2, B3)
2153: 
2154: Bulk writes run as **jobs** ([ADR-036](DECISIONS.md#adr-036--a-batch-is-a-job-one-mechanism-for-bulk-writes-imports-and-exports);
2155: design and reasons in [INTEGRATION_API P and B](INTEGRATION_API.md#p-shared-primitives)). B1 delivers
2156: object items run inline, B2 background runs and cancellation, B3 relationship items and set
2157: replacement.
2158: 
2167: 
2168: ### Request
2169: 
2185: 
2186: - **Context:** `workspaceKey` for live data, or `changeSetId` with `expectedChangeSetVersion`;
2187:   exactly one (`422 INVALID_BATCH_CONTEXT`; a change set without its version is
2188:   `409 CHANGE_SET_REQUIRED`). A job in a change set claims the version once for all its items: it
2189:   advances by one when anything changed, and not at all otherwise.
2190: - **`policy`** (required, no default): `atomic` applies every item or none; `independent` applies each
2191:   item on its own. Items apply in order, each against the data the items before it left, so a later
2192:   item sees an earlier applied one (a child after its parent). In `atomic` the first rejection rolls
2193:   everything back and every other item is `unprocessed` (`BATCH_ROLLED_BACK`).
2194: - **`run`** (required): `inline` runs the job in the request and answers `200` with its outcomes;
2195:   `background` queues it and answers `202` with the job ([Background jobs](#background-jobs)). The
2196:   size never switches the run.
2197: - **`stage`** (0.9 K2): `execute` (the default) or `preview`, which runs the items without writing
2198:   anything and waits for confirmation ([Previewing a batch](#previewing-a-batch-09-k2)). A preview
2199:   is a background job: with `run: inline` it is `422 REQUEST_VALIDATION_ERROR`.
2200: - **`onExisting`**: `reject` (default) or `overwrite`, for upserts that find a record and carry no
2201:   `expectedVersion`.
2202: - **`otherWorkspaceIds`**: `refuse` (default) or `counterparts` (0.9 J5). Record IDs are unique
2203:   across the instance, so an ID another workspace's record holds names nothing here and creating a
2204:   record with it is refused (`OBJECT_ALREADY_EXISTS`, `REFERENCE_NOT_FOUND`, both naming that
2205:   workspace). With `counterparts` such an ID stands for its **counterpart**, this workspace's own
2206:   record derived from it ([Counterparts](#counterparts-base-09-j5)): created with the counterpart's
2207:   ID the first time, found by it after. IDs this workspace's records hold, and IDs no record holds,
2208:   are used as given. An ID of a record whose workspace runs another model has no counterpart: its
2209:   item is refused `COUNTERPARTS_ACROSS_MODELS` (0.11 M4, D44).
2210: - **`Idempotency-Key`** header (optional, 1–200 printable characters), scoped to the route and the
2211:   workspace. The same key with the same request answers the original job's response again with
2212:   `Idempotent-Replayed: true` and runs nothing (a background job: `202` with the job as it is now);
2213:   with another request it is `422 IDEMPOTENCY_KEY_REUSED`; while its job is queued or running,
2214:   `409 IDEMPOTENCY_IN_PROGRESS` with `Retry-After`. A key lives as long as its job; past retention it
2215:   counts as new. Without a key, retrying a `create` without an
2216:   `id` can create the record twice; an upsert, or a create with an `id`, is safe to retry.
2217: - **Limits** (settings, reported by `GET /capabilities` as `integrationJobs.limits`): inline,
2218:   `BATCH_MAX_ITEMS` (1,000) and `BATCH_MAX_BYTES` (5 MB body); background, `BACKGROUND_JOB_MAX_ITEMS`
2219:   (1,000,000) and `BATCH_BACKGROUND_MAX_BYTES` (50 MB body); either run, `ATOMIC_JOB_MAX_ITEMS`
2220:   (10,000) for `atomic`. Over a limit is `413 BATCH_TOO_LARGE` with `details.setting`,
2221:   `details.maximum` and the request's `items` or `bytes`. `chunkItems` reports `JOB_CHUNK_ITEMS`.
2222: 
2223: ### Items
2224: 
2225: A **record reference** is `{ "id": "…" }` or `{ "objectTypeKey": "…", "key": { "attributeTypeKey": "…",
2226: "value": … } }`, where the attribute is declared `unique` and bound to the type. It resolves in the
2227: batch's context as it stands when the item runs.
2228: 
2241: 
2242: An item's validation, refusals and audit entries are its single write's. An update or upsert whose
2243: name, parent and values equal the record's is applied as `unchanged`, whatever its version claim: it
2244: writes no version, audit entry or change. Otherwise an update needs a current `expectedVersion`
2245: (`VERSION_CONFLICT`), and an upsert that finds a record needs one too (`VERSION_REQUIRED`) unless the
2246: request declares `onExisting: "overwrite"`; then it writes over the version it read, reports it as
2247: `previousVersion` and records it in the audit entry. An upsert never changes a record's type or
2248: application (`REFERENCE_TYPE_MISMATCH`).
2249: 
2250: Relationship items are decided as the single relationship writes decide them, with the same codes,
2251: and written in bulk with the object items around them, so a chunk costs a constant number of
2252: statements whatever its mix (D35). An `ensureRelation` that would change a relationship's values
2253: needs its `expectedVersion`, or `onExisting: "overwrite"` (`VERSION_REQUIRED` otherwise; an
2254: overwrite reports `previousVersion`). A claimed set (`expectedRelationSetVersion` with
2255: `relationSetDirection`, or a `replaceRelationSet`'s version) is checked against the set as the items
2256: before it leave it (`409 RELATION_SET_VERSION_CONFLICT` with `anchorObjectId`, `direction` and the
2257: current `relationSetVersion`); [the record's relationship list](#relation-endpoints) names every
2258: set's version. A containment relationship is never an item (`IMMUTABLE_RELATION`): a parent changes
2259: through an object's `parent`.
2260: 
2261: **`replaceRelationSet`.** A target the anchor already relates to keeps its relationship: omitted
2262: `attributes` keep its values, an explicit object replaces them. The others are removed and the new
2263: ones created in the listed order, each checked as a single create over what came before, so
2264: cardinality at either end (`CARDINALITY_VIOLATION`), ancestor scope (`DUPLICATE_RELATION_SCOPE`,
2265: `RELATION_ANCESTOR_REQUIRED`) and the values answer with their single codes, pointing at
2266: `/items/{i}/targets/{j}`. A set equal to the targets is `unchanged`, whatever its version claim;
2267: otherwise `expectedRelationSetVersion` must be the set's version, or the request declares
2268: `onExisting: "overwrite"` (`VERSION_REQUIRED` otherwise). Refused as well: a required-ownership
2269: binding (`REQUIRED_OWNERSHIP_BINDING`), an empty set on a required binding, or removing a
2270: relationship whose other record requires one and has no other (`REQUIRED_RELATION`, with
2271: `details.objectId`), a record listed twice (`DUPLICATE_RELATION`), and an anchor or target of
2272: another type than the binding's end (`REFERENCE_TYPE_MISMATCH`). The anchor's set advances by one,
2273: and each record whose own set changed by one. Each relationship removed, changed or created gets
2274: its audit entry and feed entry, and one `transition` entry in the anchor's history names the
2275: previous and new targets (not in the feed).
2276: 
2277: ### Response
2278: 
2279: A processed batch answers `200` with the finished job and the first page of its outcomes (up to
2280: 1,000; later pages from `GET /jobs/{id}/items`). Read `job.result`: `applied` (every item),
2281: `partial` or `rejected` (none). A request refused as a whole creates no job; that includes a model
2282: release activated while it ran (`409 MODEL_RELEASE_CHANGED`, nothing saved).
2283: 
2308: 
2309: An outcome carries only its status's fields. `applied`: `action` (`created`, `updated`,
2310: `unchanged`, `deleted`), `id`, `objectTypeKey`, `version` (none after a live delete), after an
2311: overwrite `previousVersion` and, when the record written is a counterpart, `sourceId` (0.9 J5). A relationship item's has `relationId`, the relationship's `version`
2312: (none after a delete) and, when it claimed a set, the set's new `relationSetVersion`. A
2313: `replaceRelationSet`'s has `action` `updated` or `unchanged`, the anchor's `relationSetVersion`, the
2314: version it found (`previousRelationSetVersion`, 0.9 K3) and `relationIds` (`created`, `kept`,
2315: `removed`); its refusals name that version too (`details.relationSetVersion`). An `ensureNoRelation`
2316: that found no relationship is `unchanged` without `relationId`. `rejected`: `error` with the single write's code, or one of
2317: `INVALID_RECORD_KEY`, `MISSING_RECORD_KEY`, `REFERENCE_NOT_FOUND`, `REFERENCE_TYPE_MISMATCH` and
2318: `VERSION_REQUIRED`; `details.pointer` is a JSON pointer into the request. A `REFERENCE_NOT_FOUND`
2319: whose ID is a record of another workspace says so: the message names what the reference is for (the
2320: parent, the target, a relationship's start or end) and the workspace, and `details.workspaceKey`
2321: holds it (0.9 J4a). `unprocessed`: `reason`.
2322: Every audit entry an item writes names the job as its cause (`cause: {"kind": "job", "id"}` in object
2323: history). A job's outcomes and idempotency key are kept for `JOB_RETENTION_DAYS` (7) after it
2324: finishes; `expiresAt` says until when. Then the job is `expired`: its summary (`counts`, `result`,
2325: `error`, `progress`, times) remains, and its outcomes and key are removed, so
2326: `GET /jobs/{id}/items` answers `200` with an empty page.
2327: 
2328: ### Background jobs
2329: 
2330: `run: background` answers `202` with the job, `queued`, once the job and its items are stored; a
2331: request refused before that (context, limits, a stale `expectedChangeSetVersion`, a model release
2332: activated meanwhile) creates no job. A worker in the API process then runs it:
2333: 
2334: - **Chunks.** An `independent` job applies `JOB_CHUNK_ITEMS` (500) items per transaction; an
2335:   `atomic` job is one transaction. A chunk commits its changes, their outcomes and the job's
2336:   `progress.processed` together, so outcomes page in as chunks commit, and after a crash the job
2337:   resumes at its first item without an outcome: no item is applied twice or skipped. Items see
2338:   earlier chunks' applied items.
2339: - **Lease.** `leaseOwner` and `leaseExpiresAt` name the worker running the job; the lease is renewed
2340:   with each chunk (`JOB_LEASE_SECONDS`, 120). Another worker, or the process after a restart, takes
2341:   the job over once the lease expires; a worker stopping gracefully releases it at once.
2342: - **In a change set** the job holds the change set's claim: each chunk that changes something
2343:   advances the version by one, and `changeSetVersion` is the version the job holds (its claim while
2344:   it runs, the version it left once finished). A write to the change set by anyone else between
2345:   chunks makes the job `failed` with `CHANGE_SET_VERSION_CONFLICT`.
2346: - **Stops.** Before each chunk the worker reads the job. A cancel request finishes it `cancelled`;
2347:   a model release no longer the one the job pinned (live: the active release; in a change set: the
2348:   change set's) makes it `failed` with `error.code` `MODEL_RELEASE_CHANGED`; another refusal of its
2349:   context (a retired workspace, a lost change set claim) makes it `failed` with that error; any other
2350:   failure rolls back the chunk and makes it `failed` with `JOB_FAILED` and `details.correlationId`,
2351:   the log entry's. Items the job did not reach are `unprocessed` with `JOB_CANCELLED`,
2352:   `MODEL_RELEASE_CHANGED` or `JOB_FAILED`; chunks committed before stay applied, and `result` says
2353:   what applied. `progress.processed` equals `progress.total` once the job is finished.
2354: 
2355: `POST /jobs/{jobId}/cancel` answers `202` with the job and `cancelRequestedAt` set; it waits for no
2356: chunk or step, however long. The worker carries it out at the job's next chunk (a queued job before
2357: its first item); an `atomic` job looks for it before every 500 items it decides and before it
2358: writes them, and rolls back completely. A job of one step (a profile, a draft's dry run or
2359: inference, a mapping's inference, a profile's check) and a move's last loading step look for it
2360: once more before they commit, and end `cancelled` writing nothing of that step (0.11 N2). A dry run,
2361: an inference, a mapping inference or a profile's check asks the earlier one of its subject to stop
2362: this way; two sent at the same moment are decided one after the other, so the later one stands. An import preview waiting for confirmation (0.9 J3) is cancelled at once: it is
2363: `cancelled` with `finishedAt` set, its file removed and its preview's outcomes kept to read until
2364: retention. Cancelling again changes nothing; a
2365: finished job is `409 JOB_FINISHED` with `details.state`, an unknown one `404 JOB_NOT_FOUND`.
2366: 
2367: ### Previewing a batch (0.9 K2)
2368: 
2369: A background batch sent with `stage: "preview"` is queued and run by the worker as an
2370: [import's preview](#preview-and-confirmation) is: its first `JOB_PREVIEW_MAX_ITEMS` items run
2371: independently, whatever the policy, in one transaction that is rolled back, so no record,
2372: relationship, feed entry, audit entry or event is written and a change set keeps its version. The
2373: job then waits in `awaiting_confirmation` with `preview` (`coverage`, `items`, `counts`, `result`,
2374: `previewedAt`; no `rows`, which only an import has), and its outcomes read at `/items`, where
2375: `applied` means it would apply.
2376: 
2377: `POST /jobs/{jobId}/confirm` queues it again: the preview's outcomes are removed and the stored items
2378: run from the first as `stage: "execute"` would, so **execution is authoritative**: a record changed
2379: since its preview is refused `VERSION_CONFLICT` then, and an `atomic` batch with a refusal writes
2380: nothing. Confirm's
2381: refusals (`409 CHANGE_SET_VERSION_CONFLICT` when the change set changed since the request's
2382: `expectedChangeSetVersion`, `409 MODEL_RELEASE_CHANGED`, `410 JOB_EXPIRED`), cancelling a waiting
2383: preview and retention are the import's. The `Idempotency-Key` answers with the waiting job.
2384: 
2385: A preview whose delete items would delete anything adds `preview.deletion`: `objectCount`,
2386: `objectsByType` (`{objectTypeKey: count}`), `relationshipCount` and `retainedAssociationCount`
2387: over them all (0.9 K2b, D121).
2388: 
2389: ### Deleting with what depends on it (0.9 K2b)
2390: 
2391: A `delete` item deletes its record as `DELETE /objects/{type}/{id}` does, with its rules (D120):
2392: 
2393: - **Without `cascade`** a record with dependants (containment descendants, records it owns through a
2394:   required oriented `one-to-one` or `one-to-many` relation) or a relationship other than its
2395:   containment edges is refused `409 OBJECT_HAS_DEPENDANTS`, whose `details.impact` gives its counts
2396:   and token; a record with neither is deleted.
2397: - **With `cascade`** the item needs `deletionPreviewToken`, the token of the impact the client was
2398:   shown: without one it is refused `409 DELETION_PREVIEW_REQUIRED`; when the record's version or its
2399:   impact (a record or relationship added, removed or changed) differs from what the token confirms,
2400:   `409 DELETION_PREVIEW_CHANGED`, and nothing of that item is deleted.
2401: - **In a preview** (`stage: "preview"`) a cascading item needs no token: the preview computes each
2402:   item's impact and token, and `POST /jobs/{jobId}/confirm` puts each token into its stored item, so
2403:   execution deletes exactly what was previewed and refuses only the items whose impact changed. An
2404:   item the preview did not delete itself (refused, or gone with another item) is refused
2405:   `DELETION_PREVIEW_CHANGED` if it stands on its own at execution, and a `sample` preview's
2406:   unpreviewed items are refused `DELETION_PREVIEW_REQUIRED`: each delete is confirmed by its own
2407:   preview.
2408: 
2409: An applied delete's outcome carries `impact`: `objectCount` (the record with those going with it),
2410: `objectsByType`, `relationshipCount`, `retainedAssociationCount` and `deletionPreviewToken`; counts,
2411: never lists, since one record may own thousands (D121). The single `DELETE`'s `409` keeps its lists.
2412: 
2413: **Items are decided in order.** A record reached by several items' impacts belongs to the earliest
2414: of them, as deleting them one after another would leave it. A record an earlier item of the same job
2415: deleted (a child selected after its parent, in this chunk or an earlier one) is `applied` with
2416: `action: "unchanged"` and `deletedWithItem`, that item's index (D122); a record deleted otherwise is
2417: refused `REFERENCE_NOT_FOUND` as before. A run of consecutive delete items is decided and written
2418: together as set statements (D123): their statements do not grow with the number of items or the
2419: size or depth of their impacts. The deletions are audited per record and relationship with the job
2420: as cause (live: in the feed, each record's relationships before its records; in a change set, a
2421: `change-set-object` `deleted` entry per record, as its creates and updates have).
2422: 
2423: ### Relationships by their ends (0.9 K3)
2424: 
2425: **`ensureNoRelation`** removes a relationship named by its type and its two records, so a client
2426: removing many need not read each relationship's ID and version first, and sending the item again
2427: answers `unchanged` (D129). When a relationship of that type joins `from` to `to`, it is deleted with
2428: the single delete's rules, audit and feed entries and codes: `IMMUTABLE_RELATION` for a containment,
2429: `REQUIRED_RELATION` for a required binding, and `VERSION_CONFLICT` when `expectedVersion` is sent and
2430: stale (without it the relationship found is removed whatever its version). An item whose ends' types
2431: the binding does not allow is `INVALID_RELATION_PAIR`. Its outcome is `deleted` with `relationId`,
2432: or `unchanged` when the records are not related.
2433: 
2434: **A previewed set replacement claims what it showed** (D130). In a preview a `replaceRelationSet`
2435: needs no `expectedRelationSetVersion`: it runs as if it claimed the set's version as found, and its
2436: outcome or refusal names that version (`previousRelationSetVersion`, or `details.relationSetVersion`).
2437: `POST /jobs/{jobId}/confirm` puts that version into each stored replacement that had no claim, in the
2438: same step that carries delete tokens, so execution refuses `RELATION_SET_VERSION_CONFLICT` exactly the
2439: sets changed since the preview and applies the rest (nothing under `atomic`). A `sample` preview's
2440: unpreviewed replacements have no claim and are refused `VERSION_REQUIRED`; the UI therefore never
2441: sends a replacement larger than one preview (D131). Without a preview the claim rules are as before.

3114: ## Change feed (Base 0.9 F1, F2)
3115: 
3116: - `GET /api/v1/workspaces/{workspaceKey}/feed?after=…&pageSize=…&kind=…&objectTypeKey=…`
3117: 
3118: Every change to a workspace's live data, in commit order. Each has a **position**: a per-workspace
3119: integer, gapless and strictly increasing in commit order. A live write takes its positions under the
3120: workspace lock it already holds, so a transaction's entries are consecutive and one that rolls back
3121: leaves no gap. Change-set edits, validation and discard, and model administration change no live
3122: data and take none. The feed starts empty at revision `20261003_02`; earlier changes remain in
3123: record history.
3124: 
3132: 
3133: A containment relationship is the record's parent, which the record's entry names
3134: (`parentObjectId`); it is never an entry of its own, live or published.
3135: 
3136: **Parameters.** `after` (default `0`) is the last position the reader processed. A position is public
3137: and stable, so it is the resume token itself. `pageSize` is 1–1,000 (default 500). `kind`
3138: (`object`, `relation`, `publication`) and `objectTypeKey` are repeatable. Repeated values match any
3139: of them, and the two filters combine. `objectTypeKey` matches object entries whose type, or for
3140: `reclassified` whose previous type, is listed; relation and publication entries never match it
3141: (D34). A filtered page scans at most ten pages' worth of positions, so it may hold fewer entries,
3142: or none, with `nextAfter` advanced. A sparse filter never costs an unbounded scan.
3143: 
3144: **Response.**
3145: - `items` in position order.
3146: - `nextAfter`: the `after` to pass next.
3147: - `headPosition`: the highest committed position.
3148: - `earliestPosition`: the lowest `after` + 1 the feed answers (see Retention).
3149: 
3150: The reader is caught up when `nextAfter` equals `headPosition`. An entry:
3151: 
3169: 
3170: - **`action`:** `created`, `updated`, `deleted` and `reclassified` (with `previousObjectTypeKey`)
3171:   for objects; `created`, `updated` and `deleted` for relations; `published` and `withdrawn` for
3172:   publications, whose `id` is the publication's and `version` its number. Readers ignore actions
3173:   they do not know.
3174: - **Relation entries** carry `relationTypeKey`, `fromObjectId` and `toObjectId` instead of the
3175:   object fields; they identify the relationship after a delete.
3176: - **`changedFields` and `attributeTypeKeys`** use the record history's vocabulary: names, never
3177:   values (D16). A reader that needs values reads the record.
3178: - **`cause`** is `{"kind": "user"}` for a single write, `{"kind": "job", "id"}` or
3179:   `{"kind": "publication", "id"}`.
3180: - **`modelReleaseId`** is the release the change ran under.
3181: 
3182: **Refusals:**
3183: - an unknown workspace: `404 WORKSPACE_NOT_FOUND`
3184: - `after` below 0, or `pageSize` out of range: `422 REQUEST_VALIDATION_ERROR`
3185: - `after` past the head: `409 FEED_POSITION_AHEAD`, with `details.headPosition` (D33). Such a position
3186:   was not read from this workspace's feed, or the database was restored to an earlier state; the
3187:   reader re-reads a baseline.
3188: - `after` below `earliestPosition − 1`, `0` included: `410 FEED_POSITION_EXPIRED` (see Retention).
3189: 
3190: **Retention and recovery (F2, D8, D40).** Entries older than `FEED_RETENTION_DAYS` (default 30,
3191: reported as `changeFeed.retentionDays` by `GET /capabilities`) expire from the feed; record history
3192: keeps them. `earliestPosition` is the position of the first entry within the period, or `headPosition
3193: + 1` when every entry is older, but never more than the active publication's `feedPosition + 1`. A
3194: workspace without an active publication with a position (never published, withdrawn, or published
3195: before the feed existed) has nothing to re-read, so nothing expires and `earliestPosition` is `1`.
3196: 
3211: 
3212: To recover, the reader reads the named publication (the lists with `publicationId`), then follows the
3213: feed with `after` set to its `feedPosition`. The publication equals live data at that position, so
3214: the reader misses nothing. Or it exports live data (`details.export`, [Exports](#exports-base-09-j1))
3215: and follows the feed from the export's `output.feedPosition`, which works in a workspace without a
3216: publication too (0.9 J1, D41). A workspace without a publication still keeps every entry (D54).
3217: 
3218: A retired workspace's feed stays readable. The feed is ungated like other reads until 0.12 (D10).

4056:   released for a draft without a base, even when the draft created it again: its records would carry
4057:   over.

4063:   rewrite is undone with the step. A removal leaves a definition naming the removed element alone,
4064:   and the draft's issues point at it. `addObjectType`

4066:   application declares its `details` (below); `attachAttribute` and `allowRelation` add the
4067:   attribute or relation to the type's layout unless `"layout": false`. A removal takes with it what
4068:   exists only for the removed element (D31): its bindings, views and detail page, navigation
4069:   entries, the items naming it in other views and panels (a children or relations panel or a tree
4070:   left without its list goes too), and relation types and attribute types it alone used that the
4071:   base release does not hold. The entry's inverse stores what it took.
4072: - **Positions** (D35) are the index in the declared list, 0-based; omitted, the end; out of range,
4073:   `INVALID_OPERATION` (`outOfRange`). Where a list's items carry `order` (attribute bindings, and
4074:   panels within their region), the moved or inserted item takes an `order` between its neighbours',
4075:   and the list is renumbered 10, 20, 30… only when no whole number fits.

4078:   `invalidValue`, `unknownElement`, `keyTaken`, `alreadyAttached`, `alreadyAllowed`,

4081:   entries since `expectedVersion` (at most 100, then `details.more: true` and the history route to
4082:   page), `404 MODEL_DRAFT_NOT_FOUND`, `413 OPERATION_BATCH_TOO_LARGE` over
4083:   `MODEL_OPERATION_MAX_ITEMS` (500, `details.limit` and `details.received`).

5110: `activePublicationId`; the confirmation is as above, and a change set edited (or discarded), or a
5111: publication made, since the preview is `409 MIGRATION_REVIEW_STALE` with
5112: `reviewedChangeSetVersion`, `currentChangeSetVersion`, `reviewedActivePublicationId` and
5113: `currentActivePublicationId`. The execution migrates, switches the release and publishes the change
5114: set in one transaction: its entries follow the migration's in the feed, the change set is gone, and
5115: the summary names the new `publicationId`. If the publication fails, nothing is migrated
5116: (`MIGRATION_FAILED`). The change set's content is never changed; consumer contracts are checked at
5117: the start as on any migration, so a release whose consumer APIs lower a contract version is refused
5118: (`409 CONSUMER_CONTRACT_VERSION_REQUIRED`): install the historical model with the contract versions
5119: raised, move the change set onto it (its content fits) and migrate to that release.

5144: it is now, which becomes the change set's base (D88); it changes nothing. Its rows list each value

5169: ### Mappings between two models (delivered, X1)
5170: 
5171: A **model mapping** says what each element of a source model becomes in a target model: types,
5172: attributes, relations, parents, value maps, defaults and how existing target records are matched
5173: (D18, D106). It is stored once for the instance under its `key`, named by its two models' release
5174: keys, and checked against two releases its definition names (`sourceReleaseId`,
5175: `targetReleaseId`, D104). It changes only through operations, with history, undo and redo as a
5176: draft's (ADR-041, D105). Reads are always served; writes, operations and the inference are
5177: registered with `INTEGRATION_JOBS_ENABLED` (`capabilities.integrationJobs.createJobs`, D111).
5178: 
5200: 
5201: Each source type maps to one target type; several source types may map to one. A type entry holds
5202: its attributes (a `target`, optionally read through a `valueMap`, or `ignore: true`), the
5203: relationships the source type holds at their `from` end (`target` read from the mapped type's
5204: `direction` end, with relation attributes and `missing`), where its records stand (`parent`: under
5205: the target record of the source parent, `{"from": "source"}`, or under one record named by
5206: `objectTypeKey` and `value`; `relationTypeKey` picks a containment when the target type has several;
5207: `missing: create|refuse`; absent: at the top), how a target record not found by counterpart or
5208: origin is matched (`match`: a unique target attribute or `{"field": "name"}`), and target attribute
5209: `defaults` for a source record without a value. The record name always carries; effective periods
5210: carry when both types declare one.
5211: 
5225: 
5226: **Operations** (D107): `mapType` (`sourceType`, `targetType`; a new target forgets what named the
5227: old one), `unmapType`, `mapAttribute` (`sourceType`, `attribute`, `target` with optional `valueMap`,
5228: or `ignore: true`), `unmapAttribute`, `mapRelation` (`sourceType`, `relation`, `target`,
5229: `direction`, `attributes`, `missing`), `unmapRelation`, `setParent` (`sourceType`, `parent` or
5230: `null`), `setMatch` (`sourceType`, `match` or `null`), `setValueMap` (`name`, `values` or `null`),
5231: `setMissing` (`sourceType`, `relation` or the parent, `missing`), `setDefault` (`sourceType`, a
5232: target `attribute`, `value` or `null`), `setReleases` (`sourceReleaseId`, `targetReleaseId`: releases
5233: of the mapping's models). Each is checked against the two releases; a refusal is `422
5234: INVALID_OPERATION` with `details.pointer` at the parameter and `details.reason`: `unknownElement`,
5235: `bindingNotAllowed`, `valueTypesNotConvertible` (a value-type pair `rdm_convert_value` never
5236: converts; a pair converting some values, text to date, is accepted and its values are the move's dry
5237: run), `modelMismatch`, `inUse`, `invalidValue`.
5238: 
5239: **The inference** (D108, D109) proposes per source type its target type, attributes and parent, and,
5240: when the two workspaces' records share values, a `match` by a unique attribute the pair maps; and
5241: per relationship a mapped type holds the target relationship between the mapped types. A candidate
5242: is scored from the evidence it lists: `sameModel` (one model on both sides: identity, I34),
5243: `sameKey`, `keyTokens` (the share of the keys' words), `sameName`, `attributes` (attributes shared by
5244: key or name with convertible values), `parent`, `storedRecords` (the source type's names and unique
5245: values found among the target type's records, one statement over the two workspaces),
5246: `cardinality` and `onlyRelation`; below one point nothing is proposed. A proposal keeps its ID from
5247: one inference to the next, and its status is read from the mapping: `applied` while its entry is as
5248: it made it, `held` when the mapping decides it otherwise, `rejected` when a step that applied it was
5249: undone.
5250: 
5251: **Problems and coverage** (D110) are computed on every read. A problem has `code`
5252: (`ELEMENT_NOT_IN_RELEASE`, `BINDING_NOT_ALLOWED`, `VALUE_TYPES_NOT_CONVERTIBLE`,
5253: `ATTRIBUTE_FILLED_TWICE`), `pointer`, `side` and `message`. Coverage lists the source `types`,
5254: `attributes` and `relations` not mapped, the target's `required` attributes and `requiredRelations`
5255: nothing fills, and `parents` a source record may stand under that its target type cannot
5256: (`PARENT_NOT_ALLOWED`, `PARENT_TYPE_NOT_MAPPED`, `PARENT_REQUIRED`).

5268: ### Moves (delivered: the dry run, X2; the move, X3)
5269: 
5280: 
5281: `POST /moves` answers `202` with a queued job of kind `move` (D114). It is registered with
5282: `INTEGRATION_JOBS_ENABLED` and `MODEL_ADMIN_MUTATIONS_ENABLED` (D14, D111). `selection` names what
5283: moves (I7, D116): `types`, each with an export's `where` criteria; a subtree (`parentObjectId`,
5284: that record and every record under it); records by ID (`objectIds`, up to 10,000); or nothing, the
5285: whole workspace. A record is selected when every given part selects it; a parent or related record
5286: not selected is never pulled in. `sourceAt` is `live`, read when the job binds with the source's
5287: feed position recorded, or a publication ID of the source workspace (I30, D117). With `stage:
5288: preview` (the default) the job is the **dry run of every item** (D67) and waits in
5289: `awaiting_confirmation` with its summary (D128); until it is confirmed nothing reaches either
5290: workspace: no record, feed position, audit entry or change set. With `stage: execute` it loads at
5291: once, without waiting. `mode` is `copy` (the default, the source untouched) or `move` (below).
5292: 
5293: Each selected record becomes, in this order (D118, D133): **found by its origins**, when the chain
5294: of where it came from (each record a move created keeps its origin, D23) reaches a record of the
5295: target of its mapped type (`updateOriginal`, `foundBy: origin`: a record moved back finds its
5296: original); when that original is gone and its ID is free, it is created again under that ID
5297: (`create`, `foundBy: origin`); else **found by its counterpart** in the target
5298: (`update`, `foundBy: counterpart`; the counterpart ID as for J5's loads, derived in PostgreSQL by
5299: `rdm_counterpart`, D120); else **found by the mapping's `match`**, one target record of the mapped
5300: type by a unique attribute's value or by name (`update`, `foundBy: match`, `matchedBy`; several
5301: are `refused` with `MATCH_AMBIGUOUS` and the candidates); else **created** under its counterpart ID
5302: (`create`). Its values pass through the value map, then are converted to the target attribute's
5303: value type, then the mapping's defaults fill what the source lacks; the name always carries, and an
5304: effective period's bounds carry onto the target type's period when both declare one. Its parent is
5305: the target record of its source parent (moved along, found, or created when the mapping says
5306: `missing: create`), or one record the mapping names by type and name (found, or created with
5307: `missing: create`), or none. A relationship it holds is carried when its other end moves too or is
5308: found in the target; one the target requires into a created record rides on that record's create.
5309: The items then run through the batch path against the target's live data and are rolled back
5310: (D115), so a refusal is the target's own: its code, message and `details` as an import row's (J3).
5311: 
5312: **Rows** are read at `GET /jobs/{jobId}/rows` in their order (records as they would be created, a
5313: parent first, then relationships), filtered by `outcome`, `reason` (a reason's code) and
5314: `sourceType`, paged (ADR-030). A row has `kind` (`record`, `relationship`), `outcome` (`create`,
5315: `update`, `updateOriginal`, `refused`, `notMoved`), `reasons` (each `code`, `message`, `details` and, for the mapping's
5316: reasons, the `action` that changes it: `mapType`, `mapRelation`, `setParent`, `setMatch`, `select`)
5317: and `leftBehind` (what a moving row does not carry, at the source attribute's `pointer`:
5318: `ATTRIBUTE_NOT_MAPPED`, `VALUE_NOT_CONVERTIBLE` with the `value`, `ATTRIBUTE_READ_ONLY` for an
5319: attribute the target type holds read-only, `EFFECTIVE_PERIOD_DROPPED`). A record row names
5320: `sourceId`, `sourceType`, `name`, `selected`, `targetId`, `targetType`, `targetParentId`,
5321: `parentRow` and `possibleDuplicates` (up to 10 target records of the type and name a created
5322: record has, I4); a record the mapping creates is `selected: false`, and the parent it names by type
5323: and name has no `sourceId`. A relationship row names `relationId`, `relationTypeKey`, `fromId`,
5324: `toId`, `fromName` and `toName` (its records as they are named now, 0.11 X4), `targetRelationTypeKey`, `direction`, `targetFromId`, `targetToId`, `endRows` and `rides`
5325: (the row of the record whose create carries it). The mapping's reasons are `TYPE_NOT_MAPPED`,
5326: `PARENT_TYPE_NOT_MAPPED`, `PARENT_NOT_FOUND`, `RECORD_NOT_MOVED` (its parent or its record does not
5327: move), `RELATION_NOT_MAPPED`, `RELATION_TARGET_LEFT_BEHIND` and `MATCH_AMBIGUOUS`.
5328: 
5329: The job's **`move` summary** (D122) has `coverage: complete`, `rows`, `counts` by outcome, `types`
5330: and `relationships` with their counts by outcome, `reasons` with their counts,
5331: `attributesNotCarried` (per source type, attribute and code, with the records' count),
5332: `possibleDuplicates` (rows naming any), the `mapping` key and version it ran with, `sourceAt`,
5333: `sourceFeedPosition`, and four releases: `sourceReleaseId` and `targetReleaseId` (what the
5334: workspaces ran, or the publication's) and `mappingSourceReleaseId` and `mappingTargetReleaseId`
5335: (what the mapping names). The job keeps the selection and the mapping's definition at its version
5336: (D112).
5337: 
5338: **The move** (0.11 X3). `POST /jobs/{jobId}/confirm` (no body) loads what the dry run previewed,
5339: the source as it was read then (D129), into a **new change set of the target workspace** (D130),
5340: named `Move from <source> (<job ID>)` and opened for review over current live data; the job then
5341: names it as `changeSetId`. The items are decided again against the target as they load, and the
5342: load's outcomes replace the preview's rows. A record the move creates has its **origin** (the
5343: source workspace and record) recorded and named on its row as `origin`; on the record's history
5344: (`GET /objects/{objectTypeKey}/{objectId}/history`) each entry a move caused names it as
5345: `cause.origin` (D136). Refused at the confirmation, the job left waiting (D131): `409
5346: MOVE_MAPPING_CHANGED` (the mapping changed since the dry run), `409 MODEL_RELEASE_CHANGED` (either
5347: workspace runs another release than at the dry run), `409 WORKSPACE_RETIRED`, `422
5348: MOVE_NOTHING_TO_MOVE` (no row is created or updated); a move not waiting is `409
5349: JOB_NOT_AWAITING_CONFIRMATION`, one past its retention `410 JOB_EXPIRED`.
5350: 
5351: With **`mode: move`** (D17, D134), the load ends by opening a change set of the source workspace
5352: (`Move to <target> (<job ID>)`, `move.sourceChangeSetId`) that deletes every selected record that
5353: loaded, each with its own relationships, deepest first. A loaded record's row says what became of
5354: it in the source (`source`: `deleted`, or `kept` with its reason): one that changed in the source
5355: since it was read is copied as read and kept (`SOURCE_CHANGED`); one that a record staying depends
5356: on, such as a child the move does not carry, is kept (`OBJECT_HAS_DEPENDANTS`). A refused or
5357: not-moved row is never deleted. When nothing is deleted, no change set is opened. Publishing that
5358: change set before the copy's is `409 MOVE_COPY_NOT_PUBLISHED` (`details.changeSetId`, `state`:
5359: `open`, or `discarded`, when it can only be discarded); once the copy is published it publishes as
5360: any change set (D135). Nothing reaches either workspace's feed or consumers until its change set is
5361: published, then its ordinary events (D20).
5362: 
5363: The summary also has `mode`, `targetChangeSetId`, `sourceChangeSetId`, `sourceFeedPositionAtLoad`
5364: (the source's position when it loaded, beside the dry run's `sourceFeedPosition`), counts
5365: `updateOriginal`, and for `mode: move` `source` (`deleted`, `kept`).
